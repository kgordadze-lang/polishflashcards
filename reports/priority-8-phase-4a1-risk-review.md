# Priority 8 Phase 4A-1 — Risk Review

Each item is tagged `OBSERVED FACT` (established by this audit) or `PHASE 4A-2 DECISION NEEDED` (an unresolved question this audit surfaces but does not resolve).

## 1. Source-of-truth behavior
**OBSERVED FACT.** Source-of-truth is well-defined and mechanically re-verifiable: `editorial/verb-pattern-candidates.json` → `freeze_editorial` → `verified_runtime_from_frozen` → `content/verb-patterns.json`. Both `validate-editorial` and `validate-runtime` pass against the exact committed files. Risk here is low, not unknown, contrary to what an audit might have assumed going in.

## 2. Manual/implicit stable-ID allocation
**OBSERVED FACT.** Allocation is deterministic and automatic (SHA-256 of normalized text + keys), not manual or implicit. Risk is low for the allocation *mechanism*. Risk is **not** low for the allocation *process*: nothing prevents an author from allocating an ID by hand-computing the hash incorrectly, or by copy-pasting an ID from elsewhere and mismatching its `key`. **PHASE 4A-2 DECISION NEEDED**: whether Phase 4 authoring will use a wrapper/tool that calls `allocate_*_id()` directly (safe) versus authors constructing IDs by inspection (risk of silent mismatch that would only be caught by the recomputation check inside `validate_editorial`/`freeze_editorial`, not at authoring time).

## 3. ID collision risk
**OBSERVED FACT — low.** 48-bit digest space, zero collisions found in the current 30-lemma corpus, collision detection already exists in `RepositoryIndex`. Scaling to ~98 lemmas does not meaningfully change the collision-probability picture.

## 4. ID recycling risk
**OBSERVED FACT — mechanism is sound, untested against real data.** The tombstone validator mechanically prevents recycling/resurrection *when tombstones exist*, but zero tombstones exist in the repository today (no entity has ever been retired). This is a **coverage gap in evidence, not a defect**: the check has never fired against a real retirement. Low probability of an actual problem, since Phase 4 as scoped only *adds* lemmas and does not retire any of the released 30 or any of the frozen 68.

## 5. Missing/incomplete tombstone enforcement
**OBSERVED FACT**, folded into #4 — the code exists and is wired in; there is simply no data yet to have exercised it end-to-end in this repository's actual history.

## 6. Schema/runtime coupling
**OBSERVED FACT.** Two independent validators exist for the runtime shape: the Python-side `validate_runtime` and the JS-side `pp-verb-patterns.js` loader checks. They were built to mirror each other (`PRIVATE_RUNTIME_KEYS` is explicitly commented as "a locked cross-language contract" that "must not drift"), but this audit did not perform a field-by-field diff between the two implementations beyond what was directly read. **PHASE 4A-2 DECISION NEEDED**: whether a Phase 4 schema change (e.g. adding a `direct-speech` clauseKind, see #12 below) requires updating both `priority7_tooling.py`'s `CLAUSE_KINDS` and `pp-verb-patterns.js`'s equivalent list in lockstep, and whether a test exists to catch drift between them (not confirmed either way in this audit — a plausible but unverified test-coverage question).

## 7. Metadata-only aspect-partner limitation (corrected)
**OBSERVED FACT — resolved by direct static-code proof, upgraded from the original audit's unresolved framing.** The original wording understated the risk by resting on the JS loader's permissiveness, which the correction pass explicitly disallows as evidence (the JS loader only shape-checks an already-produced runtime file; it is not the approval/freeze gate). Direct reading of `priority7_tooling.py` establishes:

- a target `aspectPartnerIds` ID that resolves to no lemma record in the same document fails validation (`ASPECT_LINK_DANGLING`, editorial lines 2297–2300 and runtime lines 2839–2842);
- reciprocity is mechanically required, not merely declared (`ASPECT_LINK_NONRECIPROCAL` otherwise, editorial lines 2307–2310, runtime lines 2844–2847);
- both linked lemmas must additionally already own at least one pattern with a reviewed `reviewState`, or `ASPECT_LINK_UNREVIEWED` fails (editorial lines 2281–2306) — a lemma with zero patterns can never satisfy this;
- every lemma, in both the editorial and runtime schemas, is required to have a non-empty `meanings` array (`MEANINGS_REQUIRED`/`RUNTIME_MEANINGS_REQUIRED`) — `meanings: []` does not validate.

Combined, these mean a metadata-only lemma stub with no full-pattern content **cannot** participate in a validated reciprocal `aspectPartnerIds` link under the current official path — it would need real, already-reviewed pattern content (contradicting "no separate Phase 4 full-pattern record"), or the anchor's reference to it would dangle. The only currently-valid option is to encode the relationship nowhere in the schema (leave `aspectPartnerIds` unpopulated on both `zacząć`/`zaczynać` and `czytać`/`przeczytać`, as the released 30 already do for all of their own aspect pairs) and keep it as governance-report-only documentation. **PHASE 4A-2 DECISION NEEDED**: whether that governance-only treatment satisfies the Phase 3B freeze's intent, or whether a schema/contract change (e.g. a declared "metadata-only" lemma kind exempt from `MEANINGS_REQUIRED`/`ASPECT_LINK_UNREVIEWED`) is required. See `priority-8-phase-4a1-phase3b-compatibility.md` §10–11 for the full A–E derivation.

## 8. Generator side effects
**OBSERVED FACT — safe.** `priority7_tooling.py`'s CLI is explicitly documented in its own module docstring as "read-only except for an explicitly requested projected output" (the `project-fixture --output` path). `priority8_phase1_transition.py` only writes under `--write` (confirmed by reading `build()`); running it without `--write` in this audit produced no filesystem change (`git status --short` empty before/after) and only raised because it is pinned to a stale historical checkpoint.

## 9. Activity/audio coupling
**OBSERVED FACT — genuinely decoupled.** Verified both in schema (independent fields at different object levels: example-level `audioEligible` vs. pattern-level `activityEligibility`) and in the actual audio pipeline (`pp_audio_rule.verb_pattern_audio_examples()` reads only `audioEligible`). `verify_audio.py` run in this audit confirms the 45 current audio-eligible examples are fully covered independent of the fact that zero patterns have any activity eligibility. Low risk.

## 10. Private governance leaking into public runtime
**OBSERVED FACT — actively guarded, not just documented.** `validate_runtime`'s `_recursive_private_key_check` mechanically rejects ~30 named private/governance-only keys anywhere in the runtime document, and this audit's own field-by-field comparison of `editorial/verb-pattern-candidates.json` vs. `content/verb-patterns.json` found the private-only fields (`internalScope`, `key`, `evidence`, `reviewState`, `reviewEvents`, `releaseMode`, `origin`) present in editorial and **absent** from every one of the 45 released patterns/45 examples in runtime. Low risk today; this is a property Phase 4 must not regress, i.e. any new schema field added for the expansion must be explicitly classified public-runtime vs. private-only before authoring begins.

## 11. Validation gaps
**PHASE 4A-2 DECISION NEEDED** (item 8 from the Phase 3B compatibility report, restated as risk): the schema has no mechanical way to pin a required lexical word (`udział`) as part of a pattern's identity, and no mechanical way to detect an over-combined "maximal frame" pattern versus correctly-kept-alternative patterns (items 4, 6, 8, 12 of the compatibility report). All four of these are currently enforced by editorial review alone. This is a real gap the current architecture does not close, and Phase 4's ~68-lemma scale increases the number of places a reviewer could miss a violation compared to the 30-lemma pilot.

## 12. Generalized-role representation limitation
**OBSERVED FACT**, restated from the compatibility report item 6: the `ROLES` enum has no generalized-direction values (no `dokąd`/`skąd`/`gdzie`), which is actually the *correct* current state per the locked authoring rule (§6.2 of the task brief) — concrete realizations use existing roles like `target`, and the generalized framing is deliberately kept out of the schema. Recorded here only so Phase 4A-2 does not mistake the absence of a `dokąd` role for a missing feature; it is a deliberate non-feature.

## 13. Risk of Phase 4B authoring before ID policy lock
**OBSERVED FACT** (procedural, not code): this audit allocated zero production IDs and answered zero of the "Phase 4A-2 decisions needed" listed above and in the other four reports (key-naming convention, metadata-only-partner schema treatment, `direct-speech` clauseKind, udział-pinning mechanism, formatVersion-vs-patternDataRevision choice for the expansion). If Phase 4B authoring began before these are resolved, at least 8 of the 68 frozen full-pattern lemmas (`odpowiadać`, `czytać`, `pisać`, `napisać`, `powiedzieć`, `zgadzać się`, `polecać`, `radzić`) would hit the direct-speech `clauseKind` gap immediately, and the two metadata-only identities (`zaczynać`, `przeczytać`) would hit the now-confirmed schema/contract requirement immediately.

## 14. Risk of Phase 4B using the old 70 instead of the frozen 68
**OBSERVED FACT — low, given current file state.** `reports/priority-8-phase-3b-phase4-handoff.md` states the exact 68-item list and the two exclusions in one unambiguous document, and this audit independently reproduced the identical 68-item ordered list by parsing `reports/priority-8-phase-3b-final-lemma-freeze.csv` programmatically — the two sources agree byte-for-byte on lemma text and order. The main residual risk is a *future* author working from `reports/priority-8-phase-3-final-synthesis.csv` (70 rows, no `full_pattern_in_phase4` distinction visible without cross-referencing the freeze CSV) instead of the Phase 3B freeze CSV/handoff — a plausible mistake if someone opens the wrong report, not a defect in either file.

## 15. Test suite drift (corrected)
**OBSERVED FACT**, re-run and re-verified during this correction pass: `python3 -m pytest tests/test_priority8_phase1.py tests/test_priority8_phase1b.py tests/test_priority7_phase3b.py tests/test_priority7_phase5a.py -q` produces **136 passed, 19 failed, 155 total**, identically on both runs. Failures occurred within the selected historical phase-pinned suites — specifically 1 in `test_priority8_phase1.py`, 5 in `test_priority7_phase3b.py`, and 13 in `test_priority7_phase5a.py` (`test_priority8_phase1b.py` passed in full). See `priority-8-phase-4a1-runtime-pipeline-map.md` for the exact per-file counts and four reason categories (a pinned Phase 4F-I1 bundle-state check; a pinned historical commit SHA that does not contain the expected path in this checkout; cascading count/set assertions from those two; and the Phase-1A transition script rejecting the now-later authoring-context state).

The correct, non-overreaching statement is: **these failures exist on the untouched Phase 4A-1 starting baseline and were not caused by this reports-only audit** — clean-tree evidence (`git status --short` empty before/after both runs) supports that this audit did not cause them, but is not by itself why they fail; the actual cause is that several tests pin exact historical commit SHAs and an exact release-bundle state that this checkout does not currently match. They are recorded because Phase 4A-2/4B planning should be aware the existing test suite includes tests pinned to a specific historical checkpoint rather than living forward-compatible regression tests — so "tests pass" cannot be used later as a blanket safety signal without checking which specific tests are phase-relevant.
