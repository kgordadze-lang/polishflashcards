## 1. formatVersion vs. patternDataRevision — recommended semantics

Reconstructed from code and history (`priority7_tooling.py` `FORMAT_VERSION = 1`; `content/verb-patterns.json` `formatVersion: 1`, `patternDataRevision: 2`; `reports/priority-8-runtime-revision-options.md`; `reports/priority-7-frozen-data-and-persistence-specification.md` §3):

- **`formatVersion`** has never moved from 1 in this system's entire history. Its documented meaning is "incompatible data-contract semantics" — i.e., a change to the *shape* of what a legal document may contain: a new enum value in a previously-closed enum, a new field on a previously-closed object, a new top-level envelope key, a new complement type. `pp-verb-patterns.js` enforces this strictly (`runtime.formatVersion !== FORMAT_VERSION` rejects the whole document, line ~934), and every enum/shape check in both the Python and JS validators is a **closed** check (unrecognized values/keys are rejected, not ignored) — so a schema-shape change is not silently forward-compatible with an unupdated loader.
- **`patternDataRevision`** moves when the *content* changes under an unchanged contract shape — revision 1→2 (Priority 8 Phase 1A) changed only which examples were `audioEligible`, with zero shape change (`priority8_phase1_transition.py` asserts this). `priority-8-runtime-revision-options.md` already anticipates revision 2→3 as "the separately approved expansion to approximately 100 lemmas" — i.e., the 68-lemma content growth itself is framed as a **content-only** revision bump, not a format change.
- **Distinguishing rule recommended by this audit**: if a change only adds *rows* under an unchanged shape (more lemmas/meanings/patterns/examples using only fields/enum values that already validate), it is `patternDataRevision`-only. If a change adds a *new legal shape* (a new enum value, a new optional field, a new top-level key), it is a `formatVersion` change, **even if** it is additive/backwards-looking-compatible in spirit — because both validators are closed-schema and reject unrecognized shape, an "additive" field is still a hard rejection for any consumer pinned to the old `formatVersion`.

A private-only field addition (Option L2 in §3) still needs to be added to the editorial schema's allowlist, but since it is stripped before runtime projection and never reaches the JS loader or `content/verb-patterns.json`, this audit recommends treating it as **not** requiring the shared `FORMAT_VERSION` constant to increment — only `validate_editorial`'s own private-key allowlist needs updating. This is a judgment call for the human reviewer to confirm, since the codebase currently uses one shared `FORMAT_VERSION` constant for both documents.

## 2. Required-lexical-material question (task §8) — treated as a fourth architecture decision

**Audit finding: the current schema does NOT already support this cleanly.** A full-repository search for `udział`/`udzial` in `editorial/verb-pattern-candidates.json` and every `reports/priority-7-*.md` specification found zero occurrences — there is no existing mechanism, field, or convention for pinning required lexical material. `priority-8-phase-4a1-phase3b-compatibility.md` item 8 independently reaches the same conclusion (`SUPPORTED WITH EDITORIAL DISCIPLINE`, meaning representable in prose only, not mechanically enforceable). This affects `brać udział w + Locative` / `wziąć udział w + Locative`, where `udział` must remain part of the verified identity (Phase 3B freeze global constraint #5; `priority-8-phase-3b-final-lemma-freeze.md` "Retained strong aspect families").

### Options

- **L1 — Editorial-only convention, no schema change.** Encode via the pattern's `key` (e.g. `udzial-w-locative`) and prose in `learnerExplanationEn`. Zero footprint; zero mechanical enforcement that every example for that pattern actually contains the string `udział`. This is the status quo classification (`SUPPORTED WITH EDITORIAL DISCIPLINE`).
- **L2 — Private-only, non-runtime authoring field (RECOMMENDED).** Add a pattern-level, private-only field (e.g. `requiredLexicalItems: string[]`) to the **editorial** schema only — joining the existing `PRIVATE_RUNTIME_KEYS`/`FORBIDDEN_RUNTIME_KEYS` set so it is stripped before runtime projection exactly like `evidence`/`internalScope`/`key` already are (`priority7_tooling.py` lines 181–198). A lightweight, optional validator check can then mechanically confirm each of the pattern's example `pl` strings contains every listed required lexical item as a substring — cheap, non-runtime, purely an authoring-time QA aid. No JS loader change at all (private fields never reach it). No public shape change, so (per the human-confirmed judgment call in §1) no `formatVersion` increment is expected, only an editorial-schema allowlist update.
- **L3 — Public runtime field enforcing lexical presence.** E.g. a complement-level `requiredLexicalItem` string reaching the runtime document. Rejected as disproportionate: this is a two-lemma-family authoring-discipline concern, not a learner-facing concept, and would require public schema growth (`formatVersion` increment, JS loader changes) for a QA-only need L2 already serves privately.

**Recommendation: Option L2.**

## 3. Twenty-one narrowing/representation constraints (task §9)

All 21 (`priority-8-phase-4a1-phase3b-compatibility.md` items 4, 6, 8, 12; handoff's 16 disposition-level + 5 additional `KEEP VERIFIED` rows) are classified `SUPPORTED WITH EDITORIAL DISCIPLINE` — every one is *expressible* using only the existing complement/role/relationType vocabulary, but none is *mechanically enforceable* today: nothing detects an over-combined "maximal frame" versus correctly-kept-alternative patterns, and nothing stops an author from also encoding the excluded wider pattern the constraint forbids.

This audit does **not** recommend attempting to mechanically validate the 21 constraints' actual linguistic content (per task §9's own instruction not to encode all linguistic research into schema — each constraint is a distinct, narrow prose judgment, e.g. "do not encode jako + Nominative for `pracować`," which has no natural machine-checkable form). Instead, **recommend a private, non-runtime authoring manifest**: a per-lemma (or per-pattern) checklist entry — e.g. living in the same Option D2 staging artifact as `narrowingConstraintRef: "phase3b-handoff#pracować"` plus the literal constraint text copied alongside the draft record — so a reviewer promoting a lemma has the exact binding constraint visible next to the draft, rather than needing to cross-reference the handoff document from memory during a 68-lemma batch. This is tooling/process scope for Phase 4B, not a schema change, and requires no `formatVersion`/`patternDataRevision` impact.
